# Artifact Trust Public API — Test Plan

**Status:** Implemented  
**Specification:** [spec.md](./spec.md)

## Implementation goal

Deliver an unauthenticated `GET /api/public/artifact-trust` endpoint that
returns complete, verified trust evidence for one `did:artifact`, using the
active chain's public RPC and trust anchors. The test suite proves that no
unverified evidence can cross the public API boundary.

## Test layers

### Unit tests — `artifact-trust-service.ts`

Use injected public-provider, trust-anchor, candidate-query, and validator
dependencies. These tests must be deterministic and make no network calls.

| U2  | Valid artifact DID with no candidates                                                                                                     | All four SDK-aligned evidence arrays are empty; summary is `0/0/0` and `complete: true`.                                                                                                                                         | Proves absence of evidence is a successful, complete lookup.                                                    |

| U5  | Candidate's schema UID is absent from active-chain anchors                                                                                | Excluded before payload decoding; no schema-registry lookup is attempted.                                                                                                                                                        | Enforces trust-anchor schema allowlisting.                                                                      |

| U8  | Candidate is revoked                                                                                                                      | Excluded.                                                                                                                                                                                                                        | Enforces EAS revocation state.                                                                                  |

| --- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |

### Integration tests — public EAS behavior

Run against a controlled EAS fixture chain or a fully mocked EAS provider that
models event retrieval and `getAttestation` reads. The test must include the
real SDK conversion/verification boundary rather than only service stubs.

| ID  | Scenario                                                                                         | Expected result                                                                                                                           | Coverage / reason                                                                     |
| --- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| I1  | Valid recognized attestation is emitted by EAS and retrieved through public RPC                  | It appears once in the public response with decoded data and decimal-string times.                                                        | Exercises the real public RPC → EAS → schema-registry → serializer path.              |
| I2  | Mixed valid, revoked, expired, unknown-schema, invalid-proof, and unapproved-issuer events       | Only the valid event is returned; summary counts every retrieved candidate.                                                               | Verifies filtering across the complete candidate set.                                 |
| I3  | Responsibility claim with a valid controller witness / authorization history                     | Claim is included only when both the claim and authorization window validate; the controller witness is absent from every response group. | Exercises supporting authorization evidence without exposing it as artifact evidence. |
| I4  | Responsibility claim whose controller is currently authorized but was not authorized when issued | Claim is excluded.                                                                                                                        | Verifies historical, not merely current, controller authority.                        |
| I5  | Query spans more than one provider block-range chunk or SDK result page                          | Success reports the complete aggregate, not only the newest/default-window events.                                                        | Proves the complete-result guarantee against SDK defaults.                            |
| I6  | Provider fails during a later page/chunk or needed authorization read                            | Endpoint returns `502 NETWORK_ERROR`, not previously collected records.                                                                   | Proves a later dependency failure cannot leak partial success.                        |

The API response is evidence, not the adapter's final policy decision. MPAS
continues to apply its `canTrust()` policy and requires the existing explicit
operator confirmation after displaying the report. A backend network or
contract error is treated as OMATrust information unavailable, not as proof
that the plugin is untrusted or as a reason to bypass content-integrity
verification.

## Contract and regression checks

- Assert every item in every successful response has
  `verification.valid === true`.
- Assert the response uses the SDK-aligned `responsibilityClaims`,
  `securityAssessments`, `certifications`, and `otherAttestations` groups;
  `otherAttestations` remains the supported catch-all.
- Assert `verification.basis` contains only applicable explanatory mechanisms,
  and that the response does not expose redundant `checks` or `reasons`
  fields for verified-only records.
- Assert every successful response has `summary.complete === true`.
- Assert `totalQueried === totalVerified + totalExcluded`.
- Assert API timestamps and all recursively nested bigint fields are strings,
  including `0` values.
- Assert the response does not contain exclusion reasons, raw provider errors,
  server configuration, premium RPC URLs, or authorization credentials.
- Assert a client cannot induce a different result by adding arbitrary query
  parameters.
- Keep an endpoint README `curl` example synchronized with the route path and
  required query parameter.

## Definition of done

- Service, route, and Next public endpoint exist at the paths specified in the
  feature spec.
- All unit and route cases above run in the backend test command; integration
  coverage runs in the appropriate CI environment.
- The endpoint uses `getPublicRpcProvider()` and no premium-RPC or authenticated
  read path.
- README documents the public endpoint, an empty-result response, and a `curl`
  example.
- The final implementation passes `npm test`, `npm run lint`, and
  `npm run typecheck` in `omatrust-backend`.
